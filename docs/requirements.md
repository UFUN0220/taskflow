# 阶段 1 需求、角色与边界

## 角色

| 角色 | 主要职责 | 数据范围默认值 |
| --- | --- | --- |
| 普通员工 | 创建草稿、查看本人相关任务、接受/处理任务、提交审核、评论和上传附件 | SELF |
| 部门主管 | 管理本部门组织关系，查看和分配本部门任务，参与审核 | DEPARTMENT 或 DEPARTMENT_AND_CHILDREN |
| 项目经理 | 管理参与项目、项目任务和项目成员协作 | PROJECT |
| 系统管理员 | 管理用户、角色、权限、数据范围和审计查询 | 由角色显式授予 ALL，不因管理员身份自动越权 |

角色是权限集合，数据范围是另一条独立边界。前端隐藏按钮只改善体验，后端仍必须检查功能权限和数据权限。

## 核心用例

- 组织管理：用户、部门树、岗位及用户-岗位关系；项目经理通过项目负责人和项目成员关系管理项目范围；
- 权限管理：角色、稳定权限编码、角色-权限关系、角色数据范围；
- 任务协作：创建、提交、接受、处理、转交、提交审核、驳回、完成、取消、归档；
- 任务内容：评论、MinIO 附件元数据、任务操作记录；
- 提醒通知：提醒计划与站内通知分离，后续通过 MQ 和 WebSocket 扩展；
- 审计：登录、权限变更、任务关键操作、附件删除和管理员补偿操作。

## 业务规则

1. `username` 和 `employee_no` 均唯一，密码只保存哈希值。
2. 部门使用 `parent_id`、`path` 和 `level` 表示树形结构；删除部门前必须处理成员和子部门关系。
3. 权限编码保持稳定，例如 `task:create`、`task:assign`、`task:review`、`audit:view`。
4. 任务状态只能通过明确的命令流转，禁止开放任意修改 `status` 的接口。
5. 任务 `version` 用于乐观锁；状态更新必须携带旧状态和旧版本条件。
6. 一个任务用户关系唯一，`assignee_type` 区分 `PRIMARY` 和 `COLLABORATOR`；一个任务只能有一个主负责人由应用服务保证。
7. 任务操作日志记录操作者、操作类型、状态前后值和 Trace ID；审计日志记录跨模块资源访问和管理操作。
8. 附件内容存 MinIO，数据库只保存 bucket、object key、文件名、类型、大小和校验值。
9. 通知是用户最终可查询的事实记录，提醒计划是待触发的调度记录，不能用 WebSocket 发送成功替代数据库通知。
10. 阶段 1 不创建默认管理员、角色或权限数据，避免在认证阶段前固化账号和密码。
